# Jarvis Studio v0.4 Test Plan

Version: v0.4  
Scope: Capability Governance & Context Optimization

## Verification Gate

```bash
npm run verify:v0.4
```

The gate runs:

```bash
npm run typecheck && npm test && npm run build
```

`verify:v0.3` is kept as a compatibility alias to `verify:v0.4`.

## P0 Automated Coverage

- Runtime governance events:
  - `skill.registry.loaded`
  - `skill.select` with candidates, scores, matched reasons, and selected skill id
  - `tool.policy.check`
  - `context.budget.apply`
  - `context.segment`
  - `failure.detected`
  - `replay.snapshot.created`
- Permission Engine:
  - low risk tools are automatically allowed
  - medium sandbox tools are allowed under local policy
  - high risk tools return `approve`
  - critical risk tools return `deny`
- Trace import:
  - v0.4 governance events are preserved in `raw_trace_events`
  - skill selection is mapped to `skill_selection_events`
  - permission checks are mapped to `permission_decisions`
  - context budget fields are mapped to `context_snapshots` and `context_segments`
  - failures are mapped to `failures`
  - replay snapshots are mapped to `replay_snapshots`
- Eval integration:
  - failed Eval cases create Failure records
  - permission denial count is read from `tool.policy.check`
  - Eval Run version bindings use v0.4 runtime/tool/context identifiers
- Governance mutation APIs:
  - `/api/skills/:id/test` executes a Skill smoke run
  - `/api/tools/:id/enable` and `/api/tools/:id/disable` persist Tool state
  - `POST /api/permissions/policies` persists local policy config
  - `/api/failures/:id/link-fix` appends fix links
  - `/api/audit-logs` exposes mutation audit records
- Existing regression:
  - provider diagnostics remain redacted and actionable
  - remote Eval Runs still default to serial execution with transient retry
  - v0.3 Eval, human review, release gate, compare, and report workflow still passes

## Manual / Browser Smoke

- Open `/skills` and verify Skill Registry list, detail, version, permission, and selection event sections.
- On `/skills`, run a Skill test and verify the latest test result links to a Run.
- Open `/tools` and verify Tool Registry schema, risk, policy, calls, and errors.
- On `/tools`, verify Tool enable / disable actions are visible.
- Open `/tool-calls` and verify the legacy Tool Call Ledger is still available.
- Open `/approvals` and verify permission decisions render with allow / approve / deny labels.
- Open `/context` and verify before / after token budget, action, priority, and risk hints.
- Open a Run detail and verify governance summary cards: Skill, Permission, Context, Failure, Replay.
- On Run detail, use Replay Overrides with Prompt / Skill / Context / Tool Policy fields and verify the request creates a new Replay Run.
- Open `/failures` and verify evidence, suggested fix, and status transitions.
- On `/failures/:id`, verify the fix-link action appends a repair association when a Failure exists.
- Open `/experiments` and create a deterministic one-variant matrix with Skill Version and Tool Policy dimensions, then verify the best variant card and results table render those dimensions.

## Residual Risks

- Browser smoke depends on local port availability.
- OpenAI-compatible replay uses the current resolved provider profile for credentials; snapshots never store API keys.
- Human approval execution is represented as persisted decision state; resuming a blocked tool call is not yet an interactive runtime flow.
